## 一、项目概览

**一句话**：基于 RAG + Function Calling 的企业内部知识库智能问答系统，既能检索制度文档，也能查询结构化数据。

**核心技术栈**：FastAPI + FAISS + BM25 + Function Calling Agent + MySQL + Streamlit + Docker。

**核心能力**：
- 文档上传（PDF/TXT）→ 切片 → 向量化 → 建索引
- RAG 问答：向量检索 + LLM 生成，返回答案 + 引用来源
- Agent 问答：LLM 自主决策调用 `knowledge_search`（查文档）或 `sql_query`（查库）
- 混合检索（BM25 + 向量，RRF 融合），Recall@8 达 100%
- 用户认证 + admin/user 权限 + Docker 化部署

**求职定位**（按匹配度）：AI 应用开发 / LLM 应用开发 / AI Agent 开发。

## 三、RAG 检索链路（核心）

RAG（Retrieval-Augmented Generation）分三步：**切片 → 向量化 → 检索**。

### 3.1 文档切片（document.py）

- 用 PyPDF2 提取 PDF 文本，TXT 直接读
- 按句子切分（正则 `[。！？；\n]`），再用**固定长度 + overlap** 拼接
- 参数：`chunk_size=512`（字符），`chunk_overlap=50`

**为什么要 overlap**：防止关键信息被切断在 chunk 边界。比如一句完整的话被切到两个 chunk 里，overlap 能让相邻 chunk 共享部分内容，保证信息不丢。

### 3.2 向量化（vector_store.py）

- Embedding 模型：`Qwen/Qwen3-VL-Embedding-8B`（硅基流动 SiliconFlow，¥0.7/M tokens）
- 输出 4096 维向量
- 批量调用：`batch_size=20`（一次 API 调 20 条文本，减少请求次数）

**为什么选 Qwen 而不是 OpenAI text-embedding-3-small**：中文更友好、更便宜。

### 3.3 向量检索（FAISS）

- 用 `faiss.IndexFlatIP`（内积相似度）
- 入库前对向量做 `faiss.normalize_L2`（L2 归一化），这样内积 = 余弦相似度
- **IndexFlatIP 是暴力检索**：不压缩、不建倒排，直接算 query 和所有向量的内积。数据量小（<1 万）时最快最准，数据量大时线性扫描会慢。

### 3.4 文件名注入（关键技巧）

切片时把文件名注入 chunk 文本：

```python
chunks.append({"text": f"【来源：{source}】{text}", ...})
```

**作用**：让 embedding 能编码「年份/来源」信息。否则「2022」这种孤立数字只在 source 字段里，向量检索分不清年份。

## 四、混合检索：BM25 + 向量

这是本项目检索优化的核心，也是面试最可能深挖的点。

### 4.1 为什么需要混合检索

纯向量检索的问题（实测发现）：
1. **形近词/近义词区分弱**：「十四五」「十五五」「十三五」语义相近，向量几乎不可分（类似「年份串味」问题）
2. **长文档霸榜**：100+ chunks 的大文件，多个 chunk 挤占 top-k，淹没短文档

### 4.2 BM25 关键词检索

BM25 是经典的关键词检索算法，基于**词频（TF）和逆文档频率（IDF）**打分：

```
score(d, q) = Σ_t  idf(t) * (tf * (k1+1)) / (tf + k1 * (1 - b + b*|d|/avgdl))
```

- `idf(t)`：词 t 越稀有（出现文档越少），权重越高。所以「知识产权」比「规划」更能区分文档
- `tf`：词在文档中出现次数
- `k1=1.5, b=0.75`：调节参数，b 做文档长度归一化

**分词方案**：用**字符 bigram**（相邻两字成组），不引入 jieba。

**为什么 bigram 够用**：「十四五」→ `["十四","四五"]`，「十五五」→ `["十五","五五"]`，完全不同的 bigram，能精确区分。而且零依赖、可复现。

### 4.3 RRF 融合（Reciprocal Rank Fusion）

两个检索器各给出排名，融合公式：

```
RRF(d) = Σ_检索器  1 / (k + rank)     # k 通常取 60
```

**原理**：不关心具体分数（向量分数 0.8 和 BM25 分数 59 量纲不同，没法直接加权），只看**排名**。让「向量排后但关键词排前」的文档能被提上来。

### 4.4 文档级去重

融合后按 source 去重（每个文档只保留最高分的一个 chunk），解决「长文档多 chunk 霸榜」。

### 4.5 年份软排序

query 含年份时，把文件名含该年份的文档排前面（**软排序**，不硬过滤）。

**为什么不用硬过滤**：query 里的「2030」可能是「目标年份」（规划的目标时间），而非「文档年份」。硬过滤会误伤「十五五规划」（文件名写「十五五」而非 2030）。

## 五、Agent 实现

### 5.1 Function Calling 原理

不依赖 LangChain，**手写 Agent 循环**（约 80 行）。核心是 OpenAI 的 Function Calling 协议：

1. 把工具定义（name/description/parameters）作为 `tools` 参数发给 LLM
2. LLM 返回 `tool_calls`（要调哪个工具、什么参数），而非直接回答
3. 执行工具，把结果作为 `role: "tool"` 消息追加
4. 把完整 messages 再发给 LLM，直到它决定直接回答

### 5.2 Agent 循环（executor.py）

```
messages = [system, user]
for i in range(max_iterations=5):
    response = LLM(messages, tools)
    if 没有 tool_calls: return 回答
    执行工具 → 追加 assistant + tool 消息
return 超时提示
```

**关键细节**：
- `tool_call_id` 是连接「工具调用请求」和「工具结果」的纽带，必须和 LLM 返回的 id 一致
- 工具执行失败不中断循环，把错误信息回传 LLM 让它重试
- 最大 5 轮，防止死循环

### 5.3 两个工具

| 工具 | 作用 | 安全限制 |
|------|------|---------|
| `knowledge_search(query)` | 检索知识库文档 | — |
| `sql_query(sql)` | 查询数据库 | **只允许 SELECT**（防 LLM 生成 DELETE/DROP） |

**sql_query 的安全设计**：白名单校验，SQL 必须以 SELECT 开头，否则拒绝。这是防止 LLM 幻觉生成危险 SQL 的关键。

## 六、后端与数据库

### 6.1 FastAPI 结构

- `main.py`：入口，`lifespan` 启动时 `init_db` + 预置 admin 账号
- 路由用 `APIRouter` 拆分，`Depends` 做权限依赖注入
- Pydantic 做请求/响应校验

### 6.2 MySQL

- 驱动 pymysql + `DictCursor`（查出行直接是 dict）
- 三张表：`users`、`uploaded_files`、`chat_history`
- 上下文管理器 `get_connection` 统一提交/回滚/关闭

**为什么 MySQL 替换 SQLite**：更贴近企业生产环境，支持并发，简历更有分量。占位符用 `%s`（pymysql 风格，非 sqlite 的 `?`）。

### 6.3 文件去重

上传时算文件 MD5，`uploaded_files` 表 `md5_hash` 字段 UNIQUE 约束，重复文件 409 拒绝。

**为什么用 MD5 判重**：O(1) 查询，跟文件大小无关，比遍历内容比对高效得多。

## 七、权限认证

- 密码用 `hashlib.pbkdf2_hmac`（10 万次迭代）哈希，存 `salt$hash` 字符串
- 登录后发随机 token（`secrets.token_hex(32)`），存内存 dict，后端重启失效
- `require_user` / `require_admin` 作为 FastAPI 依赖，从 `Authorization: Bearer <token>` 解析
- admin/user 两角色：上传/重置限 admin，问答需登录

**为什么用内存 token 而非 JWT**：简单权限场景，内存 token 足够，避免引入 JWT 库。面试可说明「生产环境应换 JWT 或 Redis 存储」。

## 八、评测体系（面试重点）

这是简历上量化数字的来源，**面试必问，务必能讲清楚**。

### 8.1 数据集

- **34 份真实公开文档**（gov.cn 国务院政策文件 + 历年五年规划纲要），38.5 万字 / 114 万字节 / 848 chunks
- **30 题评测集**，4 类题型，每题标 `gold_keywords`（标准答案文档）：

| 题型 | 数量 | 例子 |
|------|------|------|
| 数字精确 | 8 | 「到2030年人均体育场地面积多少？」→ 全民健身计划 |
| 主题语义 | 7 | 「如何推动科技成果转化？」→ 知识产权规划 |
| 五年规划区分 | 5 | 「十四五规划讲了什么？」→ 十四五纲要 |
| 年份区分 | 5 | 「2024年公务员局信息公开情况？」→ 公务员局2024报告 |

### 8.2 核心指标 Recall@k

```
Recall@k = 命中的题数 / 总题数
命中 = 标准答案文档出现在检索返回的前 k 个结果里
```

- **Recall@8 = 100%**：30 题全中（`top_k=8` 所以对应 @8）
- **Recall@5 = 96.7%**：29 题在前 5 名内
- **年份 Top-1 命中率 = 100%**

**为什么用 Recall 不用 Precision**：RAG 的目标是把相关资料「捞回来喂 LLM」，只要正确资料在 top-k 里 LLM 就能用，所以「捞没捞到」比「捞得精不精」重要。

### 8.3 优化历程（面试讲故事的素材）

| 阶段 | Recall@8 | 改动 |
|------|---------|------|
| 纯向量（基线） | 83.3% | FAISS 内积检索 |
| +BM25 混合 | 93.3% | 解决「十四五/十五五」混淆 |
| +文档去重 + 年份软排序 | **100%** | 解决大文件霸榜 + 目标年份误判 |

### 8.4 严谨性

- 发现 embedding 服务非确定性（同一 query 两次向量差 0.007）
- 因此评测**多次运行取均值**，3 次结果一致（100%）

## 九、踩过的坑与解决

这些是面试「遇到什么困难」的最好素材：

| 坑 | 现象 | 根因 | 解决 |
|----|------|------|------|
| 年份串味 | 问「2022 发展」混入 2023/2024 | 公报正文雷同，向量对年份区分弱 | 年份精确字符串过滤 |
| 大文件霸榜 | 短文档检索不到 | 长文档多 chunk 挤占 top-k | 文档级去重 |
| 目标年份误判 | 问「2030 知识产权」返回全民健身 | 硬过滤把目标年份当文档年份 | 改软排序 |
| 代理残留 | httpx Connection error | 系统代理指向已关闭的代理端口 | 关系统代理 |
| 兜底死循环 | Agent 反复重搜超时 | 年份过滤兜底返回错年份数据 | 去掉兜底，未命中返回空 |
| 字段名猜错 | SQL 报 no such column | LLM 瞎猜字段 `file_name` | 工具描述写明字段清单 |
| load_dotenv 失效 | API key 加载失败 | 默认从 CWD 找 .env | `Path(__file__).parent/.env` |

## 十、面试高频问答

### Q1：RAG 和 Agent 有什么区别？
RAG 是「检索 + 生成」的固定流程（先检索再回答）；Agent 是让 LLM **自主决策**调什么工具、调几次。本项目两种模式都实现了，Agent 可以动态调 RAG 检索或 SQL 查询。

### Q2：为什么用 FAISS 不用向量数据库（Milvus/Chroma）？
FAISS 单机零配置、Windows 好装、适合 demo 阶段数据量。数据量大到需要分布式/持久化删除时再上 Milvus。**前提是数据量小（<1万），IndexFlatIP 暴力检索最快最准**。

### Q3：混合检索为什么能提升 Recall？
向量擅长语义模糊匹配，但形近词（十四五/十五五）区分弱；BM25 擅长关键词精确匹配。RRF 融合两者排名，取长补短，把「向量排后但关键词排前」的正确文档提上来。

### Q4：Recall@8 = 100% 是怎么测的？
30 题评测集，每题标标准答案文档。对每题跑检索取前 8 个结果，看标准答案是否在内。30/30 命中 = 100%。3 次运行取均值（因 embedding 有非确定性）。

### Q5：为什么用 Function Calling 而不是 ReAct？
DeepSeek 原生支持 Function Calling，解析更稳定；ReAct 靠 prompt 让模型输出结构化文本再解析，容易出错。手写循环约 80 行，不依赖 LangChain，理解更深。

### Q6：数据量大了怎么办？
1. IndexFlatIP → IVF/HNSW（近似检索，牺牲精度换速度）
2. 引入向量数据库（Milvus）做持久化和分布式
3. 加 Reranker 精排提升准确率
4. 混合检索 + 缓存热门 query

### Q7：怎么评估 RAG 效果？
建评测集（题目 + 标准答案），算 Recall@k（检索层）和端到端准确率（LLM 层，用 LLM-as-judge 或人工）。本项目做了检索层评测，Recall@8 = 100%。

### Q8：为什么要文档级去重？
检索返回的 chunk 可能大量来自同一个长文档，挤占 top-k，导致其他相关文档排不进来。去重后每个文档最多一个 chunk，结果多样性更好，Recall 更高。

### Q9：为什么用 pbkdf2 而不是 bcrypt？
Python 标准库 `hashlib` 自带 pbkdf2，无需额外依赖。原理都是慢哈希（加盐 + 多轮迭代）防暴力破解。生产可用 bcrypt/argon2。

### Q10：遇到的最大挑战是什么？
「年份串味」问题——向量检索分不清同系列不同年份的文档。最终理解到**向量适合语义模糊匹配，精确枚举值（年份）要用字符串匹配**，这个认知贯穿了后续的混合检索设计。

## 十一、可进一步优化方向

这些是面试「如果继续做会做什么」的展示思考深度：

1. **Reranker 精排**：检索后用交叉编码器（如 bge-reranker）对 top-k 精排，把 Recall@5 也拉到接近 100%
2. **多轮对话记忆 + Query Rewrite**：让 Agent 有上下文，能处理「那 2022 年呢」这类指代
3. **SSE 流式输出**：回答逐字返回，降低感知延迟
4. **多 Agent / Supervisor**：拆成「检索 Agent + SQL Agent + 汇总 Agent」协作
5. **RAGAS 评估**：引入端到端问答质量评估，不只测检索层
6. **缓存 + 异步**：热门 query 缓存、上传建索引异步化
